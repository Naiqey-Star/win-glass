# win_glass v1.1.0 —— 托盘菜单滑块：实现方案与排障记录

> 这一版在托盘右键菜单里加了两个分段式透明度滑块。
> 功能本身不复杂，但踩到一个**静默失败**的坑：消息常量写反。
> 本文把方案、根因、定位手法和回归测试都记下来，避免以后重犯。

---

## 一、要解决的问题

| 需求 | 说明 |
| --- | --- |
| 两个滑块 | ① 非聚焦最低透明度（5% ~ 95%，默认 40%）② 聚焦最高透明度（5% ~ 100%，默认 100%） |
| 分段式（步进）样式 | 一格 = 1%，点亮几格就是百分之几，**不是**连续平滑条 |
| 步进 1%，值恒为整数 | 不能出现 41.5% 这种值 |
| 放在托盘右键菜单里 | 不弹新窗口、不加新的交互入口 |
| 值要持久化 | 下次启动沿用 |

## 二、为什么必须「自绘 + 消息钩子」

Win32 的弹出菜单**没有滑块控件**：

- `TrackPopupMenu` 期间菜单跑自己的一套模态消息循环，普通子窗口控件
  （`msctls_trackbar32`）塞不进去；
- 菜单项只能是文字 / 位图 / 自绘三种，没有第四种。

所以只能自己画：

| 环节 | 接口 | 作用 |
| --- | --- | --- |
| 建项 | `InsertMenuItemW` + `MFT_OWNERDRAW` | 菜单里留一块自己画的位置 |
| 定尺寸 | `WM_MEASUREITEM` | 回 300×42（两行：标题+数值 / 分段条） |
| 绘制 | `WM_DRAWITEM` | 用系统给的 `hDC` + `rcItem` 自己 `FillRect` 出分段条 |
| 拖动 | `SetWindowsHookExW(WH_MSGFILTER)` | 钩住**菜单模态循环内部**的鼠标消息 |
| 跟手重绘 | `InvalidateRect` + `UpdateWindow` | 值变了只重画这一项 |

## 三、根因：`WM_MEASUREITEM` 与 `WM_DRAWITEM` 的值写反了

### 症状

- 菜单里两个滑块的**位置占着，但一片空白**；
- 菜单项尺寸**怎么设都是默认的 203×16**，`WM_MEASUREITEM` 明明收到了、
  `itemWidth/itemHeight` 也写进去了；
- 用 `ctypes` 逐字节 dump 内存，确认**写的地址、偏移都对**
  （`p.contents` 与系统内存是共享的，已单独验证过）。

### 真相

| 消息 | 正确值 | 源码里写的 |
| --- | --- | --- |
| `WM_DRAWITEM` | **0x002B** | 0x002C ❌ |
| `WM_MEASUREITEM` | **0x002C** | 0x002B ❌ |

这两个常量**极其容易记反**，而且写反之后：

- **不会报错**，`TrackPopupMenu` 一切正常；
- 消息**照样收得到**，计数、日志都正常；
- 只是「拿到的是另一个结构体」：
  - 把 300×42 写进了 `DRAWITEMSTRUCT` 的 `itemAction` / `itemState` →
    系统根本不看这两个字段来定尺寸；
  - 绘制时又按 `DRAWITEMSTRUCT` 去读 `rcItem`，而缓冲区其实是
    `MEASUREITEMSTRUCT`，`rcItem` 位置是残留数据 → 画到屏幕外 → 整项空白。

### 怎么定位的（手法可复用）

1. **打「消息号 ↔ 结构体形状」对照**（`probe_map.py`）
   一条一条记下 `msg` 与 lParam 缓冲区的前 8 个 int32：

   ```
   0x002C WM_DRAWITEM      [1, 0, 10, 0, 16, 0, 10, 0]
   0x002B WM_MEASUREITEM   [1, 0, 10, 1, 256, 0, 1057888117, 0]
   ```

   看到 `itemData`（我们设的 10/11）在 0x2C 缓冲区里落在 **+24**、
   在 0x2B 缓冲区里落在 **+56** —— 而 `MEASUREITEMSTRUCT` 的 `itemData`
   正好在 +24、`DRAWITEMSTRUCT` 的正好在 +56。**两个结构体被换过来了。**

2. **逐字节 dump**（`probe_raw.py`）
   把两个结构体的原始内存打出来，反证偏移量没读错。

3. **变体实验**（`probe_swap.py`）
   分别「只在 0x2B 写宽高 / 只在 0x2C 写宽高 / 两边都写」，实测菜单项尺寸：

   ```
   只写 0x2B → 滑块项 (203, 16)   ← 没生效
   只写 0x2C → 滑块项 (338, 42)   ← 高度精确 42，生效了
   ```

4. **画个色块看**（`probe_dc.py`）
   在「有真实 HDC 的那一次通知」上把 `rcItem` 涂成纯红，截图确认菜单里
   真的出现红块 → 绘制侧字段也确认无误（`hDC` 在 +32、`rcItem` 在 +40）。

### 修复

```python
WM_DRAWITEM, WM_MEASUREITEM = 0x002B, 0x002C
# ！！踩过的坑，别改回去 ！！
# 写反了不会报错、消息照样收得到，只是「拿到的是另一个结构体」
```

同一行定义 + 醒目注释固定下来，并在 README 的「坑」表里留了记录。

## 四、同批修掉的其他问题

| 问题 | 症状 | 原因 / 修复 |
| --- | --- | --- |
| 滚轮无反应或乱跳 | 滚多少都不动，或方向不对 | 滚轮增量在 **`lParam` 高 16 位**；原先从 `wParam` 高位取，取到的是光标 y 坐标 |
| `--no-config` 启动即崩 | `float() argument must be ... not 'NoneType'` | `apply_saved({}, None, None)` 原样返回 `(None, None)`，构造函数 `_to_pct(None)` 直接 TypeError。**新机器首次运行也会崩**（因为还没有 config.json），只是带着自己生成的配置文件反复测试永远发现不了 |
| `MFT_OWNERDRAW` 静默失败 | 菜单里根本没有滑块 | 值必须是 `0x00000100`；写成 `0x00001000` 时 `InsertMenuItemW` 返回 `ERROR_INVALID_PARAMETER(87)` |
| 诊断明细无限增长 | 常驻进程内存缓慢上涨 | 消息明细封顶 64 条 |

## 六、已知限制

- 高度是精确的 42px；**宽度会被系统再加一段菜单留白**（本机实测 300 → 338），
  所以断言写成「不小于」。绘制与命中判定都按**实际矩形**来算，不受影响。
- 滚轮能否进到菜单里取决于系统消息路由；**合成的滚轮事件**在自动化里常常被投到
  前台窗口而不是菜单的模态循环，因此 `menu_e2e_test.py` 里滚轮只做**信息输出**，
  逻辑正确性由 `slider_test.py` E 段直接喂消息保证。
- 第三方外壳增强工具（StartAllBack / ExplorerPatcher / Windhawk / Winstep 等）
  会挂钩菜单代码，理论上可能干扰自绘菜单项。
- **另一个 win_glass 实例在跑会让测试结果不可信**：它会不断把 `WS_EX_LAYERED`
  重新挂回窗口，导致「退出后已还原」类断言假性失败。
  `robustness_test.py` 现在会检测并明确告警。
