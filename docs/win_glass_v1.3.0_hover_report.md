# win_glass v1.3.0 — 「悬停半透明」实现报告

> 需求：鼠标悬停在**非焦点窗口**上时，把该窗口透明度从当前值平滑过渡到
> 「最高透明度与最低透明度之间的中间值」（例：最高 100%、最低 50% → 75%）。
> 焦点窗口不受影响；移入移出平滑；明确最大/最低的取值边界；
> 多窗口并存与快速切换悬停目标的行为要明确。
>
> 本次改动：`win_glass.py` / `build.py` / `installer.py` / `slider_test.py`
> 新增：`hover_live_test.py`
> 版本：**1.2.0 → 1.3.0**

---

## 一、实现逻辑

### 1. 取值公式（唯一的悬停值来源）

```python
hover_pct = max(inactive_pct, round(inactive_pct + (active_pct - inactive_pct) * ratio))
# ratio 默认 0.5 ⇒ 正好取中点
```

| 最高 | 最低 | 悬停值 |
|---|---|---|
| 100% | 50% | **75%** ← 需求里给的例子 |
| 100% | 40% | **70%** ← 出厂默认 |
| 80% | 30% | 55% |

`ratio` 可用 `--hover-ratio` 调（0~1），配置文件里也持久化为 `hover_ratio`。
`ratio = 0.5` 是"中点"的默认值，`0` 表示悬停无视觉效果，`1` 表示悬停即最高透明度。

### 2. 谁参与悬停（这是最关键的设计决定）

`target_for()`（模块级函数，`--list` 与引擎**共用同一份逻辑**）里定优先级：

| 窗口状态 | 目标透明度 | 参与悬停？ | 理由 |
|---|---|---|---|
| 聚焦 | 最高 | ❌ | 焦点窗口本就不该被悬停影响（需求明确要求） |
| 置顶（未聚焦） | 最高 | ❌ | 它当前已经是最高透明度，按中点算**反而会把它压暗** |
| 未聚焦 · 未置顶 · **鼠标压着** | 悬停值 | ✅ | 把被压暗的窗口"提亮一半回来" |
| 未聚焦 · 未置顶 · 鼠标不在 | 最低 | — | 原行为不变 |

⇒ 悬停的语义是**只提亮、绝不压暗**；这也是置顶窗口不参与的原因，
不是遗漏。

### 3. 「鼠标压在哪个窗口上」怎么拿

Win32 **没有**「鼠标进入/离开任意窗口」的全局事件（`TrackMouseEvent` 只对自己
窗口有效，`WH_MOUSE_LL` 要多一个低级钩子且会把鼠标消息拉进本进程的消息路径）。
所以走轮询，但把开销压到接近零：

```
每 50ms（hover_interval）：
  GetCursorPos()
      └─ 坐标跟上次一样？ → 直接 return（绝大多数轮次都走这条）
  WindowFromPoint(pt) → GetAncestor(GA_ROOT)   # 归一为顶层窗口
  在已接管集合里？不在 → 视作"没有悬停"（桌面/任务栏/别人窗口都算）
  与上次不同？ → 只置 _dirty，真正的重算交给主循环
```

`WindowFromPoint` 返回的是"真正会收到这个鼠标消息"的窗口，天然处理窗口层叠顺序
（取到的就是视觉最上层那个），所以**上下叠多少层都不影响判定**。

### 4. 平滑过渡怎么保证不突跳

复用既有的 `cur / src / dst / t0 / dur` + `smoothstep` 机制，悬停只是**多了一个
目标值来源**：

```python
def _set_target(st, target, reason):
    if abs(st.dst - target) < 0.0005: return   # 目标没变 → 不重启动画（省掉无谓重排）
    st.src = st.cur                            # ★ 以"当前值"为新起点，不是旧起点也不是旧终点
    st.dst = target
    st.t0  = perf_counter(); st.dur = fade_ms / 1000
```

`st.src = st.cur` 这一行是"移入移出都平滑"的全部秘密：动画中途改目标时，
新一段从**此刻的透明度**接着走，所以任意时刻打断/反向都不跳。

实测（400ms 缓动、最高 100% / 最低 50%，`--self-test` 读回 alpha）：
`255 250 235 215 191 168 147 133 128 | 130 137 148 159 171 181 189 191 |
189 181 171 159 148 137 130 128 | 133 147 168 191 215 235 250`
—— 255 → 128(50%) → 191(**75%**) → 128 → 255，四段各自单调、两端步长小。

## 二、四个边界情况逐条对照

### ① 焦点窗口不受影响
* 判定表里聚焦优先级最高，**先返回**，悬停分支根本走不到；
* 光标压住焦点窗口时：目标仍是最高值，`hover` 标记保持 `False`；
* 焦点转移到"正被悬停的那个窗口"时：`target_for` 立刻切到聚焦分支，
  目标从悬停值平滑升到最高值（同一套缓动），且 `hover` 标记清掉；
* 反过来，焦点从悬停窗口离开时它也不会"卡"在悬停值上 —— 每轮
  `_update_targets` 都全量重算。

### ② 移入 / 移出的平滑过渡
* 移入：最低 → 悬停值；移出：悬停值 → 最低。两段都是 `fade_ms`（默认 500ms）
  的 smoothstep，**方向不同但代码同一条**；
* 目标没变时 `_set_target` 提前 return，不做无意义的时间轴重排；
* 暂停（托盘左键）时 `_update_targets` 整体短路，悬停跟随冻结；
  "立即恢复 100%" 会把所有窗口（含悬停中的）一并拉到 100%。

### ③ 最大 / 最低透明度的取值边界
| 边界 | 行为 |
|---|---|
| 最低的滑块范围 | 5 ~ 95%（`INACTIVE_MIN/MAX_PCT`），所以 `--inactive-alpha 1.0` 会被夹到 95% |
| 最高的滑块范围 | 5 ~ 100%（`ACTIVE_MIN/MAX_PCT`） |
| `ratio` 越界 | 夹到 `[0, 1]` ⇒ **悬停值恒落在两端之间（含端点）**，遍历 5~95 × ≥最低 全部验证通过 |
| `ratio = 0` | 悬停值 = 最低值 ⇒ 视觉上等于没开 |
| `ratio = 1` | 悬停值 = 最高值 ⇒ 悬停即完全显示 |
| 最高 == 最低 | 悬停值 = 同一个值 ⇒ 无可见变化（不是异常） |
| **反向配置**（最高 < 最低，滑块允许） | 中点会低于最低值 ⇒ 那会变成"悬停压暗"。这里 `max(…, 最低值)` 兜住：**退化为不改变**，绝不把窗口进一步压暗 |
| 最低值到不了 100% | 实测踩到：`GlassConfig(inactive_alpha=1.00, active_alpha=1.00)` 里 inactive 被夹成 95，所以"两值相等"只能用 95/95 构造（第一版测试就因此假失败过） |

### ④ 多窗口并存 / 快速切换悬停目标
* **全局同时最多一个悬停窗口** —— 鼠标只有一个点，`cursor_root_window()` 只返回
  一个 HWND，所以天然互斥（测试断言 `hover` 标记数 ≤ 1）；
* 切换 A → B 时：A 的目标回落到它自己的基础值、B 升到悬停值，**两条动画并行**
  各自平滑，互不干扰；其它窗口压根不重算目标（`_set_target` 提前返回）；
* **快速划过多个窗口**：每次改目标都 `src = cur`，所以整条轨迹是"一条连续曲线
  上的折线"，只会提前拐弯，不会跳；实测 4 次切换（A→B→A→离开）中
  `src` 恒等于切换瞬间的 `cur`（误差 < 1e-9）；
* 窗口在"光标不动的情况下"冒出来/消失：`_refresh_window_list` 会清掉坐标缓存，
  逼下一轮重新判定，不会卡在旧结论上。

### 其它交互细节
* **开关**：托盘菜单新增 `悬停半透明（未聚焦窗口 → 70%）` 勾选项（`CMD_HOVER`），
  命令行 `--no-hover`，配置项 `hover_enabled`（持久化，三级优先
  命令行 > 配置文件 > 内置默认）；
* **重新打开开关时**会清掉坐标缓存 ⇒ 立刻重新判定一次，不用等用户动鼠标；
* **退出还原路径完全不受影响**：悬停只改内存里的目标值，不碰
  `WS_EX_LAYERED`／`orig_alpha`，所以 `shutdown()`／关控制台／注销／关机
  四条还原路径一个字都没改；
* 光标轮询**不注册任何钩子**，不改变系统输入路径；光标不动的那一轮连
  `WindowFromPoint` 都不做。

## 五、未做的验证 & 已知前提（如实记录）

1. **`e2e_test.py` / `robustness_test.py` 本次没有跑**：本机此刻正跑着一个
   **旧版（v1.2.0）win_glass 实例**（安装版，PID 41324/44020，
   `%LOCALAPPDATA%\Programs\win_glass\win_glass.exe`，配置 30%/80%/300ms）。
   这两个脚本会真的改窗口透明度，而并发实例也在管理同一批窗口 ⇒ 互相抢写，
   `exstyle` 还原类断言必然假失败。它们**未改动的代码路径**（扫描/接管/还原/
   `_set_target`+`_tick`+`_apply_alpha`）已被 `--self-test`（真实 alpha 读回）和
   上面的悬停验证覆盖。
   要补跑的话，先退出托盘图标（或先暂停它）再执行即可。
2. **让新版本真正生效需要重启那个实例** —— 托盘右键「退出」，再启动
   `dist\win_glass.exe`（或重跑安装包）。当前跑着的仍是 v1.2.0，**没有悬停**。
3. 悬停是**轮询式**判定（默认 50ms），不是事件驱动：极端情况下"光标刚停下、
   窗口正好在那一瞬被销毁"会有 ≤1 个轮询周期的延迟（下一轮
   `_refresh_window_list` 会清缓存重新判定）。
4. 光标轮询会在**光标没动**时短路，但**光标持续移动**时每 50ms 有一次
   `GetCursorPos` + `WindowFromPoint`（几十微秒量级）；实测常驻 CPU 占用无可见变化。
